# Corelia

Основа настраиваемого продукта для работы с документами и процессами. Java 25, Spring Boot 4.0.8, Maven. Пять приложений запускаются независимо; Corelia владеет правилами изменения документов; DataSpace и DAM хранят данные, BPMN исполняет существующие процессы.

Рабочий контур состоит из сервисов Corelia и библиотеки контракта Platform V. Пользовательский интерфейс подключается к универсальному API gateway.

## Сервисы

| Приложение | Ответственность |
| --- | --- |
| `corelia-gateway` | Внешний универсальный API и сборка ответов сервисов для React-клиента |
| `corelia-auth` | Вход, обновление и завершение сессии через заменяемый провайдер; сейчас Keycloak |
| `corelia-document-service` | ПДС и КИД ОПС: реквизиты, версии, права изменения и состав вложений |
| `corelia-workflow-service` | Запуск процессов, чтение задач, выполнение вариантов завершения из BPMN |
| `corelia-attachment-service` | Загрузка, скачивание и версии файлов; метаданные в DataSpace, содержимое в DAM |

`corelia-common` и `corelia-platform-v` — библиотеки, а не отдельные процессы. `corelia-system-tests` — проверки взаимодействия. Приложения не зависят от JAR других приложений: общаются через внутренний HTTP API.

Название gateway подходит для внешней точки входа. Он выполняет агрегацию ответов сервисов для клиента; Spring Cloud Gateway здесь не используется: приложение собрано на Spring MVC и Java HttpClient.

## Локальный запуск в Docker

Нужны работающий Docker с Compose, OpenSSL и `keytool` из JDK. Для сборки вне Docker — Java 25 и Maven 3.9+. На Mac с установленным Homebrew OpenJDK:

```bash
cd /Users/ilyabaykalov/Projects/aplana/sber-npf/corelia
export JAVA_HOME=/opt/homebrew/opt/openjdk/libexec/openjdk.jdk/Contents/Home
cp -n .env.example .env
# Заполните в .env адреса и идентификаторы вашего стенда, если они ещё не перенесены.
./scripts/up.sh
# Запуск без выполнения тестов при сборке образов:
./scripts/up.sh --skip-tests
```

Gateway доступен по `http://localhost:7170`. Другой порт: `CORELIA_GATEWAY_PORT=7171 ./scripts/up.sh`. Настройка адреса API клиента в таком случае выполняется отдельно.

```bash
curl --fail http://localhost:7170/api/core/v1/health
docker compose ps
docker compose logs --tail 100 corelia-gateway
./scripts/down.sh
```

Логи читаются из stdout контейнеров: `docker compose logs -f corelia-gateway corelia-document-service`.
Интеграционные события выводятся строкой `сообщение JSON`, а `X-Request-Id` позволяет связать
запрос gateway с вызовами внутренних сервисов. Уровень задаётся `CORELIA_LOG_LEVEL=INFO`.

Скрипт запуска генерирует сертификаты, собирает образы и ждёт готовности сервисов. На хост опубликован только gateway, только на loopback. Внутренние сервисы требуют mTLS даже для healthcheck. Их адреса и сертификаты уже связаны в Compose. Пустые параметры Platform V допускают запуск, но операции платформы вернут 503. Healthcheck подтверждает запуск приложения, а не доступность внешнего стенда.

`.env` и `.local` исключены из Git и контекста Docker-сборки. Закрытый ключ локального CA не передаётся контейнерам. Сертификаты действуют 90 дней. Это локальный стенд; порядок ротации и границы защищённого контура описаны в [эксплуатации](docs/operations.md).

## Сертификат Platform V в контейнерах

Для стенда с самоподписанным сертификатом получите сертификат у администратора
или сверьте с ним SHA-256 отпечаток скачанного сертификата:

```bash
openssl x509 -in "$HOME/Desktop/platform-v.crt" -noout -subject -issuer -fingerprint -sha256
./scripts/trust-platformv.sh "$HOME/Desktop/platform-v.crt"
./scripts/up.sh --debug
```

Скрипту нужен собранный образ `corelia/auth:local`. Он копирует стандартное
хранилище доверенных CA из Java этого образа, добавляет сертификат и сохраняет
результат в `.local/platformv/cacerts`. `up.sh` автоматически подключает
`compose.platformv-tls.yaml`, когда этот файл существует. Настройка применяется
ко всем пяти сервисам и сохраняется после пересоздания контейнеров. Проверка
сертификатов и имени сервера остаётся включённой; внутренний mTLS использует
своё отдельное хранилище. Пароль `changeit` защищает целостность хранилища
публичных сертификатов, приватных ключей в нём нет.

После смены сертификата стенда или обновления Java в образе повторите импорт
и запуск. При ручном `docker compose up` добавляйте
`-f compose.yaml -f compose.platformv-tls.yaml` и, для отладки,
`-f compose.debug.yaml`. Импорт сертификата в Java на Mac контейнеры не меняет.

## Отладка микросервисов из IDE

Запустите локальный контур с JDWP (команда также пересоздаёт уже запущенные
контейнеры с настройками отладки):

```bash
./scripts/up.sh --debug
```

| Сервис | Host | Port |
| --- | --- | --- |
| `corelia-gateway` | `localhost` | `5005` |
| `corelia-auth` | `localhost` | `5006` |
| `corelia-document-service` | `localhost` | `5007` |
| `corelia-workflow-service` | `localhost` | `5008` |
| `corelia-attachment-service` | `localhost` | `5009` |

В IntelliJ IDEA:

1. Откройте Maven-проект `corelia/pom.xml`, дождитесь импорта и выберите JDK 25.
2. В **Run → Edit Configurations → + → Remote JVM Debug** создайте конфигурацию
   с именем сервиса. Выберите **Attach to remote JVM**, транспорт **Socket**,
   Host `localhost` и порт из таблицы. В **Use module classpath**, если поле
   доступно, выберите соответствующий модуль сервиса.
3. Нажмите **Debug**, поставьте breakpoint в коде сервиса и выполните действие
   в React или отправьте запрос через gateway `http://localhost:7170`.
   Для отладки нескольких сервисов подключите отдельную конфигурацию к каждому.

JVM запускаются с `suspend=n`: сервисы работают и проходят проверки готовности
без подключённой IDE. Каждый контейнер слушает JDWP на порту `5005`, а Compose
публикует его на отдельном порту только на loopback хоста. JDWP не требует
mTLS-сертификатов приложения; эти порты предназначены для локальной отладки.
Долгая остановка на breakpoint может вызвать таймаут у вызывающего сервиса
или ошибку healthcheck; после продолжения при необходимости повторите запрос.

Порты можно изменить переменными `CORELIA_*_DEBUG_PORT` из `.env.example`,
например `CORELIA_DOCUMENT_DEBUG_PORT=5017 ./scripts/up.sh --debug`.
После изменения исходников повторите запуск с `--debug`, чтобы пересобрать
образы, затем подключите IDE заново. Для отключения отладки выполните
`./scripts/up.sh` без флага: контейнеры будут пересозданы без JDWP.

При ручной работе с Compose используйте оба файла для сохранения режима:
`docker compose -f compose.yaml -f compose.debug.yaml up -d`.
Как и при обычном ручном запуске, задайте `CORELIA_UID` и `CORELIA_GID`
по `id -u` и `id -g` для доступа к локальным сертификатам.
Проверить публикацию порта можно командой
`docker compose port corelia-document-service 5005`, а запуск JDWP —
`docker compose logs corelia-document-service` (строка
`Listening for transport dt_socket at address: 5005`).
Если IDE не подключается, проверьте режим запуска и выбранный порт;
если breakpoint не срабатывает — соответствие исходников собранному образу
и прохождение запроса через выбранный сервис.

## Настройка заказчика и новые документы

Каждый заказчик разворачивает отдельную систему в своём контуре. Адреса интеграций и параметры запуска задаются через переменные окружения; модель данных, права и BPMN настраиваются в Platform V.

API `/api/core/v1` возвращает карточку с `typeCode`, `attributes`, `status` и контекстом workflow. Клиент использует этот универсальный контракт; правила изменения документов принадлежат Corelia; действующие BPMN создают сущности и меняют статусы в платформе.

Поддерживаются ПДС и КИД ОПС. Реестр видов описан в `DocumentTypes`, политики — в document-service; интеграция находится в `corelia-platform-v`, точные разрешённые GraphQL-запросы находятся в его ресурсах `graphql/`. Добавление нового типа требует настройки модели, прав и процесса в платформе, а также реализации соответствующего контракта в сервисах. Нового микросервиса для каждого вида документа не требуется.

Подробности: [API](docs/api.md), [архитектура и решения](docs/architecture.md).

## Сборка и проверка

```bash
./scripts/test.sh
# Дополнительно: проверка собранных Docker-образов на тестовой платформе.
docker compose build
./scripts/test.sh -DdockerSmoke=true
```

Тесты запускают пять настоящих приложений с mTLS и имитацию DataSpace/BPMX/BPMU/DAM/Keycloak. Проверяются универсальные документы, вложения, задачи, JWT и права сервисов. Docker-проверка использует отдельный Compose-проект `corelia-smoke` и удаляет его контейнеры после выполнения. Рабочий стенд в проверках не используется.

Maven создаёт обычный JAR и исполняемый `*-exec.jar`. Например, отдельная сборка gateway: `mvn -pl corelia-gateway -am package -DskipTests`. Для локального запуска JAR потребуются те же адреса, mTLS-ключи и пароль, что в Compose; для первого запуска удобнее использовать готовый Docker-сценарий.

Порядок проверок и границы имитации платформы: [testing.md](docs/testing.md).

## Внешняя конфигурация

При запуске требуется customer package. Для Compose задайте `CORELIA_CUSTOMER_CONFIG` абсолютным путём к пакету на хосте; для JVM — `CORELIA_CONFIG_PATH`. Встроенных схем заказчика в продукте больше нет. Порядок подготовки и ограничения миграции: [конфигурация](docs/configuration.md).
