# Корневой репозиторий и подмодули

Корневой Git-репозиторий Corelia хранит общие файлы сборки, запуска и документацию,
а также конкретный коммит каждого из восьми подмодулей:

- corelia-auth
- corelia-document-service
- corelia-attachment-service
- corelia-workflow-service
- corelia-gateway
- corelia-common
- corelia-platform-v
- corelia-system-tests

История каждого модуля остаётся самостоятельной. Родительский коммит фиксирует
совместный состав проекта через gitlinks. Исходные ветки и коммиты модулей при
подключении сохранены. Административные каталоги перенесены стандартной командой
`git submodule absorbgitdirs` в `.git/modules/`; файл `.git` внутри модуля указывает
на соответствующий каталог. Не удаляйте корневую `.git`: теперь там хранится
также локальная история подмодулей.

## Текущее состояние адресов

Удалённые репозитории пока не настроены. В `.gitmodules` используются относительные
адреса `./corelia-document-service` и аналогичные для остальных модулей. Без origin
они разрешаются относительно этого локального репозитория. Такая конфигурация
позволяет клонировать проект из существующей папки на этом компьютере.

Пример клонирования текущего локального проекта из другой папки:

```bash
git -c protocol.file.allow=always clone --recurse-submodules \
  /Users/ilyabaykalov/Projects/aplana/sber-npf/corelia corelia-copy
```

Доступ к локальному протоколу разрешён только на время этой команды; глобальную
настройку Git менять не нужно. Локальные `.env`, `.local`, сертификаты, настройки
IDE и результаты сборки в репозиторий и клон не входят.

Перед публикацией на Git-сервер нужно создать удалённый репозиторий для корня
и отдельные удалённые репозитории для всех модулей. Для каждого подмодуля настроить
origin, опубликовать нужные ветки и теги, затем заменить его URL в `.gitmodules`:

```bash
# Вместо URL_МОДУЛЯ передать реальный адрес соответствующего репозитория.
git -C corelia-document-service remote add origin URL_МОДУЛЯ
git -C corelia-document-service push -u origin feature/model-versioning
git submodule set-url corelia-document-service URL_МОДУЛЯ
```

Повторить для всех восьми модулей. Если нужна вся прежняя история веток и тегов,
опубликовать также соответствующие ветки и теги, а не только feature/model-versioning.
После настройки всех адресов закоммитить `.gitmodules`, добавить origin корня
и опубликовать корневую ветку. Отправка одного корневого репозитория не отправляет
историю модулей. Текущие локальные URL не предназначены для клонирования с Git-сервера.

## Изменение микросервиса

Работать из корня Corelia. Сначала закоммитить исходники внутри модуля:

```bash
git -C corelia-document-service status
git -C corelia-document-service add src
git -C corelia-document-service commit -m "Исправлено сохранение версии документа"
```

Затем зафиксировать новую ссылку на коммит в корне:

```bash
git add corelia-document-service
git commit -m "Обновлена версия сервиса документов"
```

Для согласованного изменения нескольких сервисов сначала создать коммиты в каждом,
затем одним родительским коммитом обновить все соответствующие gitlinks.
Изменения только общих файлов (`pom.xml`, `compose.yaml`, `docs`, `scripts`)
коммитятся непосредственно в корневом репозитории.

После настройки удалённых адресов сначала отправлять коммиты модулей, затем корня.
Для проверки доступности ссылок можно использовать `git push --recurse-submodules=check`.

## Получение зафиксированного состава

После клонирования без `--recurse-submodules` или переключения корневой версии:

```bash
git submodule update --init --recursive
git submodule status --recursive
git status
```

Для локальных файловых адресов перед `submodule` добавить одноразовое
`-c protocol.file.allow=always`, как в примере клонирования.

`update` получает именно записанные родителем коммиты, а не последние версии веток.
Свежий клон обычно оставляет подмодули в detached HEAD. Перед разработкой перейти
на нужную ветку внутри соответствующего модуля; в исходной рабочей папке сохранены
ветки `feature/model-versioning`. Перед переключением состава сохранить локальные
правки коммитом или stash; не использовать `--force` для обхода конфликтов.

Обычная сборка Maven и Docker Compose продолжает использовать прежние пути.
В Docker-контекст не входят ни корневая `.git`, ни файлы `.git` подмодулей.

Документация Git: https://git-scm.com/docs/git-submodule
