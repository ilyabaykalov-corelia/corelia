# Версии документов

Бизнес-правила версий реализованы в `corelia-document-service`. DataSpace хранит
текущую карточку, снимки версий и результаты идемпотентных команд. BPMN не изменён.

## Поведение

- `PdsContract.id` и публичный `documentId` постоянны. Процесс и задачи продолжают
  ссылаться на существующий документ; команда версии не вызывает BPMX/BPMU mutations.
- Одно сохранение изменённых `contractDate`, `contractNumber`, `snils` создаёт одну
  новую версию. Нормализованные совпадающие атрибуты не повышают номер.
- Статус согласования остаётся в постоянной карточке и не версионируется.
- Атрибуты версии неизменяемы. JSON-состав вложений текущей версии меняется при
  загрузке, замене и удалении. После появления следующей версии прежний состав
  больше не меняется. Новый состав изначально наследует прежний.
- JSON в `PdsContractVersion.attachments` содержит метаданные конкретных версий
  вложений, их публичные идентификаторы и ссылки на хранение. Это прикладной снимок,
  а не DataSpace historization. Файлы не копируются; отдельные relational links
  в этой реализации не используются. Ссылочную целостность состава обеспечивает ядро.
- История вложения возвращает версии строго меньше выбранной версии файла.
  Удаление убирает только текущую привязку и признак `Attachment.current`, не удаляя
  метаданные и бинарное содержимое старых версий.
- Историческая карточка в React доступна только для просмотра. Статус и маршрут
  явно обозначены как текущее состояние общего процесса.

## Первая версия и совместимость

BPMN по-прежнему создаёт `PdsContract`. После появления карточки ядро создаёт v1.
Чтение и любая запись также идемпотентно инициализируют v1, если предыдущий запрос
прервался после создания документа. Два параллельных инициатора защищены `compare`
и уникальным индексом `(document, version)`.

У старых документов v1 — снимок состояния на момент включения версионирования
для этого документа, с автором/временем инициализации. Это не восстановленная
история с даты первоначального создания. Прежние версии файлов остаются доступны.
Между созданием карточки внутри BPMN и инициализацией v1 есть восстанавливаемое окно;
общей транзакции между BPM и DataSpace нет.

Номер договора и СНИЛС, уже скопированные BPMN в переменные/атрибуты задач,
автоматически не обновляются. Карточка читает актуальные данные из DataSpace.
Изменение решений процесса, зависящих от таких копий, не входит в механизм версий.

## Согласованность и права

Все команды изменения атрибутов и состава проходят через document-service.
attachment-service загружает бинарное содержимое в DAM и вызывает внутреннюю
команду фиксации метаданных. mTLS допускает этот маршрут только для attachment-service.
Для проверки назначения document-service может читать workflow-контекст; завершающие
задачи маршруты для него не открыты.

Изменение атрибутов, замена и удаление вложения разрешены назначенному оператору
на шаге `IN_WORK`. Первоначальная загрузка доступна создателю в `CREATED`.
Проверки ядра не заменяют пользовательский JWT и permissions платформы.
Инициализация вынесена в отдельную разрешённую читателям операцию, изменения
защищены отдельным `DocumentVersion:commit` для оператора/владельца приложения.

Каждая из операций `commitDocumentAttributes`, `commitDocumentNoChange`,
`commitDocumentFileUpload`, `commitDocumentFileReplace`, `commitDocumentFileDelete`
содержит проверку `changeToken` и исходных атрибутов,
обновление карточки, необходимые для команды изменения версии/метаданных файла и запись
результата команды. Это один пакет DataSpace с `X-DSPC-multiaggregate: true`:
Отсутствующие команды и их переменные полностью исключены из соответствующей
операции; условные директивы и фиктивные ID не используются.
Существующие Attachment остаются самостоятельными агрегатами, без опасной смены
принадлежности заполненных сущностей. Новые версии и команды — дочерние сущности
существующего PdsContract. Инициализация не требует многоагрегатного пакета.

`changeToken` — прикладной непрозрачный токен конкурентных изменений, не номер
версии и не история DataSpace. Он меняется также при изменении состава вложений.
BPMN меняет только статус и не обязан знать этот токен. Отдельная транзакция
изменения статуса и чтение исполнителя не составляют общей транзакции с командой:
этот механизм не обещает атомарного согласования решения пользователя с BPM.

Каждая команда получает UUID `requestId`. Хеш ключа включает документ и пользователя.
`DocumentCommand` сохраняет хеш входных данных и ответ в той же транзакции. Повтор
возвращает сохранённый ответ; тот же ключ с другим содержимым даёт 409. Время
подготовки файла исключено из хеша, поскольку повторная загрузка формирует его заново.
Пакетная загрузка файлов — последовательность отдельных идемпотентных команд,
а не одна транзакция всех файлов: при сбое повторять весь исходный запрос с тем же
requestId (дочерние ключи выводятся из номера элемента).
Форма создания сохраняет идентификатор уже созданного документа, исходный состав
файлов и requestId при ошибке загрузки. Кнопка повторной загрузки использует
тот же документ и ключ, поэтому не создаёт дубликат документа или уже сохранённых файлов.

Файл загружается по адресу `documents/{id}/uploads/{uploadId}/{sha256}/{fileName}`,
не зависящему от вычисляемого номера версии. Повтор с изменённым содержимым не
перезапишет уже закреплённые байты. DAM и DataSpace не имеют общей транзакции.
Неудачная фиксация может оставить незакреплённый файл. Автоматическое удаление
таких файлов не реализовано: очистка требует отдельного согласованного DAM API и
проверки отсутствия ссылки во всех версиях. До этого не удалять uploads по возрасту.

## API

- `GET /api/core/v1/documents/{type}/{id}` — текущая версия и состав вложений.
- `GET /api/core/v1/documents/{type}/{id}/versions` — список версий, автор и время.
- `GET /api/core/v1/documents/{type}/{id}/versions/{number}` — выбранная версия.
- `PATCH /api/core/v1/documents/{type}/{id}`:

```json
{
  "requestId": "7bb8eb14-51a6-4f92-a0bf-14fb00447de1",
  "expectedVersion": 1,
  "changeToken": "токен из последнего GET",
  "attributes": { "contractNumber": "ПДС-42" }
}
```

Загрузка и замена файлов требуют `requestId` рядом с `attachments`.
Удаление: `DELETE /api/core/v1/attachments/{id}?requestId={uuid}`.
Клиент должен повторять неопределённо завершившийся запрос с исходным ключом и телом.
При 409 перечитать карточку, сохранить пользовательские правки отдельно и явно
повторить их на новом состоянии. Сервер не затирает конкурентные изменения.
Старые клиенты, не передающие поля конкуренции/идемпотентности, требуют обновления.

## Деплой в текущую тестовую среду

Каждый деплой полностью заменяет файлы платформы и сбрасывает прежние документы.
Сохранение данных между деплоями и миграция сейчас не требуются. История версий
сохраняется в пределах работы среды между деплоями.

1. Собрать полный архив существующим
   `bash sber-npf-platform-v/scripts/package-platform-v.sh` из общей папки.
   Отдельный скрипт или архив для версионирования не нужен.
2. Развернуть полный комплект платформы обычным способом со сбросом тестовых
   данных. BPMN входит в общий комплект; его исходная схема не изменена этой задачей.
3. Обновить corelia и React из соответствующих веток. Новая модель и permissions
   должны быть установлены до обработки запросов новым corelia.
4. Проверить на установленной платформе поддержку `Text`, `parent`, составного
   unique-индекса, GraphQL `compare` (включая null при инициализации v1)
   и передачу `X-DSPC-multiaggregate` до DataSpace Core.
5. Создать новый документ, запустить работу по нему и проверить инициализацию v1,
   изменения файла до v3, создание документа v2, замену файла до v4, чтение обоих
   составов, удаление текущего файла и продолжение той же активной задачи.
   Проверить два конкурирующих сохранения.

Откат в этой среде — сборка и полный деплой стабильных веток со штатным сбросом
тестовых данных. Перенос документов и их версий при таком откате не требуется.

## Проверки и границы доказанности

Локальные HTTP/mTLS интеграционные тесты используют PlatformStub, а не рабочий
DataSpace. Проверяются сценарий v1/v3 → v2/v4, сохранение задачи и ID, просмотр
старых файлов после удаления, no-op, повтор и подмена requestId, потерянный ответ,
ошибка транзакции, конфликт редакторов и изменение вложения при открытой форме.
React проверяется сборкой TypeScript/Vite.

Успех тестов имитации не подтверждает принятие схемы конкретным дистрибутивом
СберТех. Компиляция модели и smoke-тест реального DataSpace обязательны перед
установкой на рабочий контур; в рамках этой реализации стенд не изменялся.
