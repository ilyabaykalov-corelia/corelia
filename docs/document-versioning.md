# Общий документ и прикладные версии

Механизм версий принадлежит `corelia-document-service`. DataSpace хранит состояние
и обеспечивает транзакции; historization СберТех не используется.

## Модель

- `Document` — конкретный корень агрегата. Общие поля: `documentId` (unique),
  `documentType`, `createdBy`, `createdAt`, `version`, `changeToken`.
- `PdsContract` — дочерние реквизиты с уникальной родительской ссылкой `document`.
  Поля: `contractDate`, `contractNumber`, `snils`, `status`. Обратная ссылка
  `Document.pdsContract` задаёт связь один к одному. Реквизиты не наследуются
  от Document: используется композиция.
- `KidOps` — дочерние реквизиты КИД ОПС со ссылкой `document` и обратной связью `Document.kidOps`; состав полей описан в [kid-ops.md](kid-ops.md).
- `DocumentVersion` — общая сущность снимков для всех видов документов.
  Содержит `document`, индексированный `documentId`, `version`, `schemaVersion`,
  `attributes` (Text с JSON), `attachments` (Text с JSON), `createdBy`, `createdAt`,
  `closedAt`. Пара `(document, version)` уникальна.
- `DocumentCommand` — дочерние результаты идемпотентных команд:
  уникальный `commandKey`, `requestHash`, JSON `response`.
- `Attachment` — самостоятельный агрегат метаданных конкретной версии файла.
  Общий `logicalAttachmentId` объединяет историю содержимого; `documentId`
  указывает владельца. Связь строковая, её согласованность обеспечивает ядро.

`Document`, реквизиты выбранного вида, версии и команды входят в один агрегат через
`parent` / `mappedBy`. Версий отдельных типов, в том числе PdsContractVersion,
в модели нет. Бинарные файлы хранятся в DAM и при создании версии не копируются.

## Правила версий

Одно сохранение изменённых атрибутов создаёт одну версию. Совпадающие после
нормализации значения номер не повышают. Атрибуты снимка неизменяемы.

Состав вложений текущего снимка меняется при загрузке, замене и удалении файла.
При создании следующей версии прежний состав фиксируется (`closedAt`), новый
снимок наследует его. Пример: документ v1 / файл v3 → изменение атрибутов →
документ v2 / файл v3 → замена файла → документ v2 / файл v4. У документа v1
остаётся файл v3. История файла содержит только версии меньше выбранной.
Удаление текущего вложения не удаляет прежние метаданные и бинарное содержимое.

`status` принадлежит дочерним реквизитам вида (PdsContract или KidOps), не включается в JSON атрибутов и не повышает версию.
Историческая карточка доступна только для просмотра; её статус и маршрут
обозначают текущее состояние общего процесса.

Общий `DocumentVersionService` не знает списка реквизитов ПДС. `DocumentPolicy`
задаёт валидацию, версию схемы и права вида; зарегистрированы
`ConfiguredDocumentPolicy` с версией схемы из внешнего registry (для СберНПФ — 1). Неизвестная версия схемы отклоняется явно:
автоматического преобразования исторических JSON пока нет.

## Создание и BPMN

Процесс ПДС пока создаёт документ. Операция `createPdsContract` теперь содержит
два создания в одном пакете: `createDocument`, затем `createPdsContract` со ссылкой
`document: "ref:createDocument"`. BPMN сохраняет ID дочерних реквизитов в переменной
`id` и обновляет только их `status`. Шаги, роли, решения и переходы сохранены.
Публичный `documentId` и оба внутренних ID постоянны между версиями.

После появления документа ядро инициализирует v1. Чтение и запись повторяют
инициализацию, если первый запрос прервался. Инициализация и создание в BPM
не составляют общей транзакции; это восстанавливаемое окно.

Процессная переменная и параметр решения `approvalStatus` сохранены. Поле модели
и состояние карточки React называются `status`. Скопированные при старте реквизиты
в переменных и атрибутах задач автоматически не обновляются. Новая версия не
вызывает запуск процесса, завершение задачи или смену шага.

## Согласованность и права

Все изменения атрибутов и состава идут через document-service. Для ПДС редактирование,
замена и удаление доступны назначенному оператору в IN_WORK; первоначальная загрузка
также доступна создателю в CREATED. Проверка исполнителя читает workflow-контекст.
Отдельное изменение статуса BPMN не атомарно с такой проверкой прав.

Команды `commitDocumentAttributes`, `commitKidOpsAttributes`, `commitDocumentNoChange`, `commitDocumentFileUpload`,
`commitDocumentFileReplace`, `commitDocumentFileDelete` используют статические пакеты
без условных директив и фиктивных ID. Проверка `Document.changeToken`, изменение
состояния и запись результата команды выполняются вместе. При изменении атрибутов
в тот же пакет входят обновление реквизитов соответствующего вида с compare исходных значений,
создание DocumentVersion и закрытие предыдущей версии.

При PATCH реквизитов клиент передаёт `expectedVersion` и `changeToken`. Для файловых команд ожидаемое состояние читает document-service. Токен меняется также при изменении
вложений. Конфликт возвращает 409: нужно перечитать карточку и повторно применить
пользовательские правки к актуальному состоянию.

`requestId` — UUID. Ключ команды хеширует документ, пользователя и requestId;
сохраняются хеш входных данных и ответ. Повтор возвращает сохранённый ответ,
подмена содержимого при том же ключе возвращает 409. При потерянном ответе
фиксации ядро проверяет сохранённый результат команды.

Сервис вложений получает вид документа через внутренний `GET /documents/by-id/{id}`
и передаёт команду состава в API его вида. Доступ к `attachment-commands` разрешён
только сертификату attachment-service. Сам сервис не определяет правила редактирования.

DAM и DataSpace не имеют общей транзакции. Содержимое сначала загружается по адресу
`documents/{id}/uploads/{uploadId}/{sha256}/{fileName}`, затем фиксируются метаданные.
Сбой может оставить незакреплённый файл; автоматической очистки нет.
Пакет файлов — последовательность отдельных идемпотентных команд. Повторять нужно
исходный состав и порядок с тем же requestId. Форма создания при ошибке загрузки
сохраняет в своём состоянии ID созданной карточки и данные для повтора вложений.

## Добавление следующего вида

Новая таблица версий не нужна. Потребуются сущность реквизитов и обратная связь
общего Document, политика вида, адаптер чтения/сохранения его реквизитов с атомарным
пакетом, permissions, регистрация вида и форма React. Нельзя автоматически считать
статусы и правила ПДС общими для всех видов.

Сейчас каталог, поиск, создание и адаптер типизированных реквизитов поддерживают
ПДС и КИД ОПС. Особенности второго вида описаны в [kid-ops.md](kid-ops.md). Общая таблица и алгоритм версий готовы для расширения, но произвольный вид
не становится поддерживаемым только после добавления строки в DocumentType.

## Проверки и установка

Актуальные команды и границы проверки — в [testing.md](testing.md). Изменения модели, permissions, BPMN, Corelia и клиента должны составлять совместимый комплект. Проверить оба вида документов, создание v1, сценарий v1/v3 → v2/v4, сохранение текущей задачи, status без новой версии, конфликты и повтор загрузки.

Локальная имитация не запускает SDK-генератор DataSpace и не подтверждает исполнение реальных пакетов и permissions. Для существующих данных и запущенных процессов требуется явный план совместимости или миграции; автоматический сброс не является процедурой обновления.
