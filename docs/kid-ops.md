# КИД ОПС

Код вида — `KID_OPS`, название — «КИД ОПС». Вид доступен в общем выборе при
создании, реестре и на главной странице. Существующая карточка не меняет вид.

## Атрибуты

Все поля обязательны, кроме отчества. Системный вид хранится в Document.documentType.
Реквизиты — в дочернем `KidOps` с обратной ссылкой `Document.kidOps`:

| Поле | Ограничение |
| --- | --- |
| contractNumber | До 64 символов, строго ОПС-123-4567-1234567 |
| contractDate | Корректная календарная дата; API YYYY-MM-DD, интерфейс использует календарь |
| signingYear | Целое число 1000–9999; в форме ровно четыре цифры |
| lastName | До 40 символов |
| firstName | До 255 символов |
| middleName | До 256 символов, пустое значение нормализуется в пустую строку |
| snils | 14 символов, строго 123-456-789 00 |
| status | CREATED, IN_WORK, STORED; не входит в атрибуты версии |

Проверки выполняются в ядре (`ru.corelia.document.KidOps`) и повторяются в форме
для удобства. Статус нельзя передать через PATCH атрибутов.

## Версионирование системы

Используется существующий DocumentVersion с schemaVersion=1, JSON атрибутов и
составом вложений. Отдельной таблицы версий КИД ОПС нет. Изменение атрибутов создаёт
версию, замена файла меняет только состав текущей версии. Закрытые версии сохраняют
свой состав. Статус не повышает номер версии. Сохранение реквизитов KidOps,
Document.changeToken, нового снимка и результата команды выполняется одним пакетом.

## Процесс

`Process_kid_ops_storage` в `kidOpsStorage.bpmn`:

Начало → создание документа с первым вложением → «Взять в работу» → запись
IN_WORK → работа назначенного оператора → «Отправить на хранение» → запись
STORED → конец.

Переход на хранение не создаёт новую версию. После него API запрещает изменение
атрибутов, загрузку, замену и удаление файлов. История и скачивание доступны.
Маршрут существующего договора ПДС не изменён.

## Обязательное вложение при создании

`POST /api/core/v1/documents/KID_OPS` получает `attributes`, UUID `requestId` и
`initialAttachment` с `fileName`, `contentType`, `contentBase64`.

1. document-service проверяет атрибуты, пользователя и наличие файла.
2. По внутреннему mTLS API attachment-service загружает непустой файл в DAM.
   Маршрут подготовки недоступен gateway и другим сервисам.
3. document-service передаёт только метаданные подготовленного файла в процесс.
4. BPMN создаёт Document, KidOps, Attachment и результат команды создания одним
   многоагрегатным пакетом. До фиксации пакета карточка не существует.
5. Ядро инициализирует общий снимок v1 с уже существующим вложением.

Форма допускает несколько файлов: первый создаётся вместе с карточкой, остальные
добавляются последовательными командами. При сбое дополнительных загрузок можно
повторить их в той же карточке. Минимум один файл уже закреплён при создании.
После создания до взятия в работу создатель может завершить первоначальную загрузку
через API; редактирование реквизитов доступно только назначенному оператору в IN_WORK.

Повтор завершённого создания с прежним requestId возвращает существующий документ;
другие данные с тем же ключом дают 409. Публичный ID выводится из пользователя и
requestId, имеет уникальное ограничение. Это не гарантия единственного запуска BPM
при параллельных запросах до фиксации: проигравший процесс может получить инцидент
уникальности. Ретраи запуска самого BPM не добавлены.

DAM и DataSpace не имеют общей транзакции: при сбое пакета может остаться
незакреплённый бинарный файл, автоматической очистки нет. При сбое загрузки DAM
процесс вообще не запускается. Инициализация v1 восстанавливается следующим чтением.

## Проверка и деплой

- `bash corelia/scripts/test.sh` — HTTP/mTLS сценарии КИД ОПС и регрессия ПДС,
  обязательность/форматы полей, отказ загрузки, версии и блокировка после хранения.
- `npm --prefix sber-npf-react run build` — TypeScript и сборка React.
- `bash sber-npf-platform-v/scripts/package-platform-v.sh` — полный архив,
  включающий новую BPMN, справочники, модель и permissions.

На тестовом стенде выпускать полный комплект со сбросом данных, затем обновить
Corelia и React. Обязательно опубликовать новый процесс и проверить его выбор
по DocumentProcessSettings. Генерацию SDK и реальное выполнение пакета BPMN
локальный PlatformStub не заменяет.
