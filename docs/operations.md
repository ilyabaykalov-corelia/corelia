# Локальная эксплуатация

## Конфигурация

Скопируйте `.env.example` в `.env`, заполните параметры стенда. Если новый локальный `.env` уже подготовлен из настроек `sber-npf-java`, повторно копировать пример поверх него не нужно. Скрипт `up.sh` создаёт файл только при его отсутствии. `.env` не публикуется в Git и не включается в образ.

Для Keycloak достаточно базового адреса realm и clientId. Отдельные issuer/JWKS/token/logout URL нужны только при отличающихся маршрутах; не задавайте их пустыми строками поверх работающего базового адреса. При необходимости поддерживаются `PLATFORM_V_KEYCLOAK_CLIENT_SECRET` и `PLATFORM_V_KEYCLOAK_SCOPE`, как в исходной реализации. Пароли конечных пользователей в конфигурацию не записываются.

При обращении из контейнера к сервису на Mac используйте `host.docker.internal` вместо localhost. Issuer JWT должен оставаться точным issuer выпущенного токена; если сетевой адрес Keycloak отличается, задайте issuer отдельно. Внутренние Corelia URL всегда HTTPS. Адреса Platform V выбираются согласно опубликованным маршрутам вашего стенда; локальная схема тестов не меняет TLS-настройки реальной платформы.

Каждое развёртывание обслуживает одного заказчика. Параметры запуска передаются через `.env` и Compose, секреты — через файлы secrets. Модель данных, права и процессы настраиваются в Platform V. Роли пользователя извлекаются из подписанного токена Keycloak; локальных исключений для отдельных логинов нет.

## Сертификаты и ресурсы

`init-local.sh` создаёт отдельный локальный CA, пять сертификатов и PKCS12 truststore. Приватный CA остаётся на хосте. Контейнер получает только свои ключи и сертификат CA. Пароль PKCS12 передаётся как Compose secret и читается через Spring configtree. Скрипт не перезаписывает существующий комплект.

После истечения 90 дней остановите Corelia, сохраните старую `.local/certs` в безопасном месте, уберите её из рабочего пути и повторно выполните `init-local.sh`, затем запустите сервисы. Это полная ротация локального CA с остановкой; бесшовная промышленная ротация здесь не реализована.

Контейнеры запускаются без root, с read-only корневой файловой системой, ограничением памяти 512 МБ и временным `/tmp`. `up.sh` передаёт UID/GID владельца локальных ключей. При прямом `docker compose up` задайте `CORELIA_UID` и `CORELIA_GID`, если они отличаются от 1000. На сборку и пять JVM нужен дополнительный запас памяти Docker.

Только `127.0.0.1:7170` опубликован на хост. Сеть backend допускает исходящие подключения к платформе; она не помечена `internal`, иначе внешний стенд оказался бы недоступен. Gateway для локальной совместимости принимает HTTP. Публичное развёртывание потребует внешнего HTTPS и собственного управления сертификатами вместо локального CA.

## Проверка и диагностика

```bash
./scripts/test.sh
# После сборки образов:
./scripts/test.sh -DdockerSmoke=true

docker compose ps
docker compose logs --tail 100 corelia-auth
docker compose exec corelia-document-service /app/health.sh
```

Все приложения пишут сообщения в stdout контейнера, поэтому отдельные файлы логов внутри образа не
создаются. Структурированные события интеграций имеют формат `сообщение JSON` и сохраняют подход
сервисов Corelia: видны DataSpace, BPMX/BPMU, DAM, Keycloak, Redis и межсервисные вызовы. Для
поиска одного пользовательского запроса используйте переданный в ответе `X-Request-Id`:

```bash
docker compose logs --follow --since 10m corelia-gateway corelia-document-service
docker compose logs --no-log-prefix corelia-document-service | rg 'DataSpace GraphQL|HTTP request'
```

Уровень событий задаётся переменной `CORELIA_LOG_LEVEL` (по умолчанию `INFO`). Сервисы не записывают
access token, refresh token, пароли и содержимое пользовательских запросов; адреса внешних систем в
событиях очищены от query-параметров.

Системные тесты требуют возможности открывать локальные TCP-порты. Перед ними `test.sh` создаёт сертификаты. Docker-сценарий работает только с имитацией платформы, запускает отдельный проект `corelia-smoke`, проверяет действия через опубликованный gateway и останавливает этот проект в блоке завершения. При аварийном прерывании процесса его можно убрать командой `docker compose -p corelia-smoke down`.

Health означает, что приложение запущено. Он не проверяет доступность всех внешних API и не гарантирует работоспособность пользовательского сценария. Для ошибок DataSpace/BPMX нужно смотреть ответ операции и состояние процесса в платформе. Сервисы не пишут access token и содержимое паролей в собственные диагностические сообщения.

## Ограничения первой версии

- Нет нагрузочных измерений и гарантии наибольшей скорости выбранного протокола. Есть проверка реального взаимодействия и TLS.
- Поиск документов пока собирает страницы и фильтрует их в Java. Предел полного сканирования — `CORELIA_DOCUMENT_SCAN_LIMIT`, по умолчанию 10 000. При превышении возвращается 422. Для больших объёмов нужен перенос фильтрации/сортировки в конкретный API DataSpace.
- Поиск задач сохраняет лимит исходного адаптера — 100 на запрос к BPMU. Метаданные вложений используют существующий поисковый контракт платформы без новой серверной пагинации. Для больших очередей и файловых реестров потребуется отдельное развитие этих контрактов.
- Файлы принимаются в base64 и буферизуются. `MAX_BODY_SIZE_MB` ограничивает JSON-тело, по умолчанию 35 МБ. Потоковые загрузки, presigned URL и оптимизацию памяти для больших файлов нужно проектировать отдельно.
- Пакет замены версии сохраняет прежнюю семантику DataSpace. Конкурентные замены и очистка осиротевшего DAM-объекта после сбоя записи метаданных не получили нового механизма согласования.
- Авторизация сохранена через Keycloak password grant. Отдельная проверка audience, распределённый rate limiting и централизованный аудит не добавлены в рамках миграции.
- Автоматического повтора изменяющих команд и сквозной идемпотентности нет. После таймаута сначала проверяйте созданный процесс/документ.
- Redis необязателен и в Compose не запускается. Если задать `REDIS_URL`, используется кэш задач Corelia; ключи учитывают пользователя и адреса платформы. Без Redis запросы выполняются напрямую через сервисы.

Эти ограничения не меняют владельца бизнес-правил: им остаётся платформа. Отдельные сервисы расчётов, подписи, уведомлений и собственного движка модели в эту поставку не входят.

## 504: пересечение Docker-подсетей с адресами платформы

8 сентября 2026 года обнаружен конфликт: `element.aplana-it.ru` разрешался в `172.19.202.54`, а пустая Docker-сеть `ecos-dev` занимала `172.19.0.0/16`. Docker перехватывал маршрут к платформе даже из контейнеров Corelia, подключённых к другой сети (`172.18.0.0/16`). С Mac публичный JWKS возвращал 200, из контейнера соединение завершалось таймаутом.

Параметры сети сохранены в `.local/diagnostics/ecos-dev-before-removal.json`. После проверки отсутствия подключённых контейнеров пустая сеть удалена. Доступ восстановился без пересборки и перезапуска Corelia. Увеличивать HTTP-таймауты не потребовалось.

При повторении сравните адрес платформы с подсетями **всех** Docker-сетей:

```bash
docker network ls
docker network inspect ecos-dev --format '{{json .IPAM.Config}} {{json .Containers}}'
```

Проверка соединения без пользовательского токена:

```bash
curl --max-time 10 -o /dev/null -w '%{http_code}\n' \
  https://element.aplana-it.ru/platformv/realms/PlatformAuth/protocol/openid-connect/certs
docker compose exec -T corelia-gateway curl --max-time 10 -o /dev/null -w '%{http_code}\n' \
  https://element.aplana-it.ru/platformv/realms/PlatformAuth/protocol/openid-connect/certs
```

При повторном запуске проекта, создающего `ecos-dev`, задайте в его Compose-конфигурации подсеть, не пересекающуюся с корпоративными сервисами и другими Docker-сетями. Сеть с подключёнными контейнерами нельзя удалять как неиспользуемую: сначала требуется согласованное изменение её проекта. Файлы соседнего проекта в ходе исправления не менялись.
