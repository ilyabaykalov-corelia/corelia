# Продукт Corelia

## Назначение

Corelia — основа настраиваемой системы работы с документами и связанными процессами. В текущем проекте пользователь создаёт карточку документа, добавляет файлы, находит документ в реестре, выполняет задачи обработки и просматривает историю изменений. React предоставляет рабочее место, Corelia — прикладные API и правила изменения документов, Platform V — хранение и исполнение существующих процессов.

Для заказчика предполагается отдельное развёртывание в его контуре. Настройка интеграций выполняется через окружение, модель и процессы — через комплект платформы. Backend загружает виды, схемы и отображение реквизитов из внешнего customer package; сохраняются типизированная модель и статические операции платформы. React и права используют внешние метаданные; полный сценарий двух заказчиков на неизменных сборках с реальным Platform V ещё не подтверждён.

## Пользователи

| Роль | Назначение в текущей реализации |
| --- | --- |
| `document_operator` | Создание и обработка документов; изменение реквизитов и файлов при разрешённом состоянии и назначении задачи |
| `approver` | Согласование договора ПДС через процессные задачи |
| `app_owner` | Управление задачами в процессах; роль учитывается проверками доступа, но не отменяет проверку назначенного оператора при редактировании |

Права определяются подписанным токеном, правилами ядра и permissions платформы. Видимость кнопки в интерфейсе сама по себе не предоставляет право выполнить действие.

## Реализованные виды документов

| Вид | Код | Реквизиты | Процесс |
| --- | --- | --- | --- |
| Договор ПДС | `PDS_CONTRACT` | Дата и номер договора, СНИЛС | Работа оператора и согласующего; согласование, отклонение, доработка |
| КИД ОПС | `KID_OPS` | Дата и номер договора, год подписания, ФИО, СНИЛС | Создание с обязательным файлом → взятие в работу → отправка на хранение |

ПДС использует статусы `CREATED`, `IN_WORK`, `ON_APPROVAL`, `NEEDS_REVISION`, `APPROVED`, `REJECTED`. КИД ОПС — `CREATED`, `IN_WORK`, `STORED`. Перечень статусов не означает разрешения произвольных переходов: доступные действия задаются текущей задачей процесса.

У КИД ОПС все реквизиты, кроме отчества, обязательны; номер имеет формат `ОПС-123-4567-1234567`, СНИЛС — `123-456-789 00`, год — четыре цифры. Проверка формата СНИЛС не должна описываться как проверка его подлинности. Полный контракт: [КИД ОПС](kid-ops.md).

## Основные сценарии

1. **Вход.** Пользователь входит через Corelia Auth и текущий провайдер Keycloak. Клиент поддерживает обновление сессии и возвращает пользователя на вход при утрате авторизации.
2. **Поиск.** Главная страница и реестр дают доступ к документам. Поиск предусматривает вид, строку запроса, статус, даты и постраничную выдачу.
3. **Создание.** Пользователь выбирает вид, заполняет реквизиты и прикладывает файлы. КИД ОПС нельзя создать без первого вложения. При сбое дополнительных загрузок форма сохраняет данные для повтора в уже созданной карточке.
4. **Работа с задачами.** Есть очереди «Мои» и доступных задач. Пользователь берёт задачу в работу и выполняет предложенное процессом действие. Произвольное редактирование статуса через реквизиты не предусмотрено.
5. **Редактирование.** Назначенный оператор меняет реквизиты и файлы в `IN_WORK`. Создатель с необходимой ролью может добавлять первоначальные файлы в `CREATED`. После отправки КИД ОПС на хранение изменения закрыты.
6. **История.** Пользователь просматривает версии реквизитов, состав файлов выбранной версии и историю содержимого вложений. Историческая карточка открывается для просмотра.
7. **Файлы.** Реализованы загрузка, скачивание, замена, удаление из актуального состава и предпросмотр PDF, DOCX, XLSX. Содержимое хранится в DAM, метаданные — в DataSpace.

## Что означает версия

Документ сохраняет свою идентичность при изменении реквизитов. Изменённые реквизиты создают следующую версию; сохранение тех же нормализованных значений не увеличивает номер. Загрузка или замена файла меняет состав текущей версии документа, при этом история содержимого файла имеет собственную нумерацию.

Пример: у документа v1 находится файл v3. Изменение реквизитов создаёт документ v2 с тем же файлом v3. Затем замена файла даёт файл v4 в документе v2; у документа v1 остаётся файл v3.

Новая версия не запускает новый процесс и не завершает задачу. Статус отражает текущий общий процесс, а не исторический снимок процесса на момент создания версии.

## Границы готовности

- Реализованы два вида документов. Универсальный API и общая модель версий облегчают расширение, но не заменяют реализацию нового вида.
- Контроль конфликтов и повторов предусмотрен для команд версионирования. Гарантии создания и запуска процесса отличаются по сценарию; нельзя обещать общую идемпотентность всех операций.
- Хранение файла и запись его метаданных не являются одной транзакцией; возможны незакреплённые файлы после сбоя.
- Наличие кода, локальной имитации и прежних отчётов не подтверждает установку актуального комплекта на стенде. Публикация модели и процессов требует отдельной проверки.

Компилятор поставляет одинаковый ac.json для адаптера и платформы; команды сохраняют проверку JWT и permissions хранилища.
