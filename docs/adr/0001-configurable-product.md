# ADR 0001: Corelia Configurable Product Architecture

Дата: 2026-09-16. Статус: принято для реализации; миграция выполняется поэтапно.

## Решение

Corelia поставляется одинаковыми JAR, Docker-образами и сборкой React всем заказчикам. Виды документов, их поля, схемы, представление, отображение хранения и процессы задаются внешним версионируемым solution package. Добавление вида не требует изменения исходников продукта. Идентификаторы заказчика допустимы в customer package и миграционных тестовых данных, но не в исполняемом продуктовом коде.

В product остаются правила версий, optimistic locking, идемпотентность, состав файлов, механизмы валидации и выполнения команд. Document-service владеет изменением документов. Attachment-service владеет содержимым; workflow-service — мостом процессов; gateway — транспортом; React — представлением.

DataSpace хранит типизированную модель заказчика. GraphQL и её служебные типы остаются в адаптерах. Компилятор solution package выдаёт статические операции, permissions fragment и контрактные fixtures из одного текста. В runtime допускается только подстановка variables; произвольной генерации операций нет.

## Конфигурация

Отдельный модуль corelia-configuration не зависит от Spring, сервисов и Platform V SDK. Документ описывается JSON Schema и отдельными UI/storage/workflow/attachments metadata. Начальный формат файла — JSON (однозначный поднабор YAML); расширение формата загрузки не меняет семантику.

CORELIA_CONFIG_PATH указывает на каталог поставки. На запуске: чтение → проверка версии → проверка структуры и ссылок → неизменяемый registry. Неизвестные обязательные возможности отклоняются. Hot reload и произвольные исполняемые выражения не поддерживаются. Используется явно документированное подмножество JSON Schema; неподдерживаемые ключевые слова нельзя молча игнорировать.

## Согласованность и совместимость

Сохраняются публичные идентификаторы, generic snapshots, schemaVersion, expectedVersion, changeToken и requestId. Проверка ожидаемого состояния, реквизиты, снимок и receipt фиксируются одним пакетом DataSpace. Это обязательный контракт будущего хранилища. Версия документа не запускает процесс.

Действующие BPMN остаются совместимыми: параметры, process IDs, уже запущенные экземпляры и существующие данные не переименовываются механически. Создание в BPM и инициализация v1 не являются общей транзакцией. DAM staging может оставлять незакреплённое содержимое; повторы запуска процесса нельзя считать гарантированно идемпотентными.

Фактическую авторизацию заказчика исполняет Platform V. Corelia предоставляет capabilities, UI их отображает. До появления проверенного платформенного контракта capabilities существующие проверки ролей/исполнителя сохраняются; конфигурация не должна превращаться в обход доступа. Удалять локальные ограничения можно только вместе с эквивалентной проверкой платформы и негативными тестами.

## Последовательность и приёмка

Сначала configuration → document policies → storage operations → compiler → перенос СберНПФ. Затем workflow, capabilities, API и UI. На каждом шаге сохраняется проверяемая совместимость; временный старый код явно учитывается в журнале прогресса.

Приёмка: регрессионные сценарии СберНПФ; отказ при некорректной конфигурации; точное совпадение GraphQL; негативные проверки доступа; CAS и повторы; два разных customer package с неизменной сборкой backend/frontend. Stub подтверждает продуктовый контракт, но не работу реальной модели, permissions и BPM; проверка реальной платформы фиксируется отдельно.
